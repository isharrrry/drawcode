# 测试与质量约束

**English** | [中文](test-and-quality.zh-CN.md)

> 本仓靠什么判断一次改动已经够好：不可让渡的质量目标、每一级测试能看见与看不见什么、什么算证据、
> 什么条件下才允许合并、数字怎么记录、残余风险落在哪里。

## 本文档的地位

本文档是契约中「质量」的那一半。[`requirements.md`](requirements.md) 规定必须成立什么；本文档规定
如何证明它成立、什么算通过、以及哪些证据不予采信。一个行为在这里是绿的、却在 `requirements.md` 里
被违反，它仍然是缺陷——以需求为准。

## 1. 范围与分工

四份文档，各管一个事实。同一个事实写两处，就是文档开始互相矛盾的起点。

| 文档 | 回答什么 |
| :--- | :--- |
| [`requirements.md`](requirements.md) | 产品必须做什么，以及明确不承诺什么 |
| [`conformance.md`](conformance.md) | 比对什么、在哪个层级比对、容差是多少 |
| [`verification.md`](verification.md) | 量到了哪些数字、由哪条命令量到 |
| **本文档** | 怎么证明、何时可合并、证据怎么记录 |

判断归属的经验：比对规则进 `conformance.md`；算术进 `verification.md`；门禁与裁决进本文档。
本文档中的数字变动时，另两份文档要在同一次改动里跟上。

## 2. 质量目标与硬约束

这些是目标，不是愿望。每一条都有落地位置，「由什么强制」一列写的是位置，不是把规则再抄一遍。

| # | 目标 | 由什么强制 |
| :--- | :--- | :--- |
| **QO-1** | 确定性：同一输入在任何一次运行、任何一台机器上产出逐字节相同的输出 | 规范 JSON 输出、L1 层逐字节的金标准比对、以及 id 稳定性测试 |
| **QO-2** | 不静默降级：处理不了的输入必须给出诊断或报错，绝不返回空结果 | 读取器的诊断契约，以及对不可读布局与畸形文档的显式拒绝测试 |
| **QO-3** | 严格的只读：检查产物从不修改它、从不执行它 | 产物测试中的只读断言 |
| **QO-4** | 核心层无第三方运行时依赖 | `implementations.md` 的依赖表，由一次干净安装验证 |
| **QO-5** | 验证可复现：任何对外公布的数字都能用文档里的命令重算 | §9 的记录纪律 |
| **QO-6** | 诚实的覆盖：没验过的必须写成「未验证」 | §10 的残余问题清单，以及 `conformance.md` 的「金标准看不见的行为」清单 |

为了省事而牺牲上述任何一条的改动，无论测试多绿都不予接受。

## 3. 测试层级与各自能看见什么

层级按代价从低到高排列。一级测试只有在它的盲区被写清楚时才有用，所以最后一列与第二列同样重要。

| 层级 | 施加对象 | 能证明 | 看不见 |
| :--- | :--- | :--- | :--- |
| **T1 — 核心单元** | 核心库，纯断言，不涉及编辑器 | 解析规则、模型派生、路由决策、规范输出 | 任何与扩展宿主、webview、真实 draw.io 客户端有关的事 |
| **T2 — 扩展单元** | 扩展自身逻辑，隔离运行 | 树与模型操作、别名处理、路径与 URI 处理 | 渲染、`vscode` API 行为、webview 消息 |
| **T3 — 金标准契约** | 提交在仓库中的用例，按 L1–L4 比对（见 `conformance.md`） | 解析契约、容器契约、几何契约、schema 合法性 | 「金标准看不见的行为」所列各项；两个金标准用例之外的一切 |
| **T4 — CLI 行为** | 命令行端到端 | 开关行为、退出码、落盘位置、构建→回写→构建的幂等 | 交互行为与视觉行为 |
| **T5 — 变异与拒绝** | 刻意破坏的输入（schema 变异、不可读载荷、损坏归档里的容器记录） | 校验器是「拒绝」而不是「放行」 | 合法输入是否被正确处理 |
| **T6 — CI** | 干净检出，单个 runner | 门禁可以从零复现 | 未使用的 runner 上的平台相关行为 |

目前存在的最高层级是**单 runner 上的 T6**。没有任何自动化层级会去看一个真实的 draw.io 窗口，也没有
任何层级在 Windows 或 macOS 上跑。这两处空白记在 §11，而不是被含糊过去。

## 4. 什么算证据

证据之所以是证据，是因为对应的失败模式能让它变红。以下按这条标准取舍：

| 采信 | 为什么 |
| :--- | :--- |
| 断言一次操作之后产出的值 | 行为错了它就会红 |
| 与提交在仓库中的用例做逐字节比对 | 任何漂移都会红，包括「看着差不多」的漂移 |
| 一条命令，且把输出的那一行原文抄进记录 | 别人重跑能得到同一行 |
| 对畸形输入的拒绝测试 | 校验器一旦开始放行它就会红 |

| 不采信 | 为什么 |
| :--- | :--- |
| 「这条规则存在」/「文件被写出来了」式断言 | 行为坏了它们照样绿 |
| 把跳过计为通过 | 跳过的契约用例会让未验证的行为看起来已验证 |
| 用截图代替断言 | 不可重复，也不可比对 |
| 只说「命令退出码 0」而不给计数行 | 退出码不携带真正重要的那个数字 |
| 从旧文档里抄来的数字 | 那是记忆，不是测量 |

跳过这条规则值得单列一行：**有五个测试是按设计跳过的，那不叫通过**。它们跳过是因为需要仓库之外的
东西（一个样本产物，或一个已编译的模板示例），跳过原因会被打印出来。日后若把某个金标准比对改成
跳过，那是回归，不是便利。

## 5. 充分性

以下条件全部成立时，测试集才算充分：

1. `requirements.md` 里的每一条需求都被 §3 的某一级覆盖，且覆盖关系在 §7 的追踪表中点名。
2. `conformance.md` 的「必需能力」表中的每一项都被施加过。在那里发生的回归，即使没有任何金标准用例
   会察觉，也算失败。
3. 「金标准看不见的行为」所列的每一项，要么在 T1 或 T2 有独立测试，要么在 §10 登记为未验证。没有
   第三种状态。
4. 每一个校验器都有一组变异用例证明它会拒绝。只有正向用例的校验器视同不存在。
5. 实际执行的用例数，等于 runner 报告的用例总数减去明确跳过的数量。不允许静默扣减。

覆盖率百分比刻意不作为充分性判据。行覆盖无法区分「断言了结果的测试」与「仅仅执行过那一行的测试」，
而本仓恰好被这个区别咬过。

## 6. 环境

| 项 | 要求 | 说明 |
| :--- | :--- | :--- |
| 门禁所用操作系统 | Ubuntu，跑在 CI runner 上 | 库与 CLI 跨平台，但门禁只在一个 runner 上跑 |
| 门禁所用 Node.js | **22.18**，在 CI 中固定 | 各 `package.json` 声明的下限是 `>=22.18`；CLI 依赖默认开启的类型擦除 |
| 开发机上的 Node.js | 不固定 | 量取 §9 数字时为 **v24.16.0** |
| .NET 运行时 | **10** 或更高，仅 PE/CLI 产物需要 | 由随包的 sidecar 使用；ELF、ar 与源码链路都不需要 |
| CI 结构 | 三个 job：`quality` 跑版本一致性与两个类型检查，`core` 跑核心测试，`extension` 安装、构建并跑扩展测试 | 三者独立，使一个失败不会掩盖另一个 |

环境同时也是限制：门禁从不在 Windows 或 macOS 上跑。路径处理、文件权限与换行符因此没有任何自动化
的跨平台证据。这被记为风险，而不是被当成已证结论。

## 7. 追踪关系

每个域映射到一组需求、一组测试层级，以及一处写有证据的地方。需求编号存放在 `requirements.md`；
下表使用与之相同的域名，因此追踪是按名称对应，而不是把编号抄进第二份文档。

| 域 | 需求分组 | 层级 | 证据记录在 |
| :--- | :--- | :--- | :--- |
| 源码→图 | `SRC` | T1、T3、T5 | `conformance.md`、本文档 §9 |
| 图→源码 | `SYNC` | T1、T4 | `conformance.md`、本文档 §9 |
| 中间表示与布局 | `IR` | T1、T2、T3、T5 | `conformance.md`、本文档 §9 |
| `.drawio` 格式契约 | `DRAWIO` | T1、T3、T5 | `conformance.md`、本文档 §9 |
| 标注语义 | `ANN` | T1、T3、T5 | `conformance.md`、本文档 §9 |
| 元数据模板 | `TPL` | T1、T5 | `verification.md`、本文档 §9 |
| 产物读取 | `ARTIFACT` | T1、T4、T5 | `artifact-format.md`、本文档 §9 |
| VS Code 扩展 | `EXT` | T2、T4 | 本文档 §9 |
| 平台与运行时依赖 | `PLATFORM` | T6 | 本文档 §6 与 §11 |
| 验证本身 | `VERIFY` | 全部层级 | 本文档 §4 与 §5 |

反向追踪就是把同一张表倒着读：一个说不出自己在保护哪个域的测试，不属于这套测试集。

## 8. 准入与准出

**准入。** 只有在依赖已安装、生成物已是最新时才能起跑。陈旧的构建产物不是测试结果：扩展测试跑的是
已构建的输出，忘记重新构建就等于在测昨天的代码。

**准出。** 每一步都跑，按下列顺序，不允许短路：

| 步 | 命令 | 通过标准 |
| :--- | :--- | :--- |
| 1 | `npm run version:check` | 每一处承载版本号的位置都被报出同一个版本 |
| 2 | `npm run typecheck` | 两个包均无错误 |
| 3 | `npm test` | 两个包零失败，且计数总数与 §9 一致 |

顺序不是装饰。版本检查放第一位，因为版本不一致会让后面每一个数字失效——被测的制品并不是要发布的
制品。类型检查放在测试之前，是为了让类型错误永远不被报成测试失败。

**不允许有条件通过。** 门禁失败就报失败，并给出失败的步骤与计数行。没有「不稳定，重跑到绿」这一步；
一个已知不稳定的测试是 §10 里的缺陷，不是重试规则。

## 9. 记录

记录规则：

1. 任何文档里的数字，都必须能在文档写明的环境上、用文档写明的命令重算出来。缺任一项，数字应删除而
   不是加限定语。
2. 一条记录带日期、运行时版本与计数输出行，因为一个光秃秃的数字无法被复核。
3. 数字变化时，持有该数字的文档必须在同一次提交里变化。过时的数字与失败的测试同级。

记录时间 **2026-11-06**，Node **v24.16.0**，仓库版本 **0.4.0**：

| 测量项 | 命令 | 结果 |
| :--- | :--- | :--- |
| 版本一致性 | `npm run version:check` | `0.4.0 in 9 places` |
| 类型安全 | `npm run typecheck` | 两个包均无错误 |
| 核心测试 | `npm run test:core` | **229 个用例：224 通过 / 5 跳过 / 0 失败**（14 个测试文件） |
| 扩展测试 | `npm run test:extension` | **93 个用例：93 通过 / 0 跳过 / 0 失败**（3 个测试文件） |
| 金标准用例 | 不是命令——用例本身提交在仓库中 | **2 个用例**（`small-c`、`small-cs`），钉住 L1–L3，且 `small-c` 另有逐字节等比 |
| VSIX 内容 | `npm run package` | **49 个文件、802,641 字节**（`drawcode-artifact-viewer-0.4.0.vsix`） |

**本次记录最初发现的一处不一致，已解决。** `verification.md` 与 `implementations.md` 曾写着
**核心 211 个测试 / 扩展 79 个测试**，那组数字是在产物读取器及其测试加入之前量到的。两份文档都已在
新增本文档的同一次改动里对齐到上表的计数。

核心侧有五个测试被跳过。跳过原因在运行时打印：它们依赖仓库不提交的产物或生成文件。它们不是失败，
也不是通过。

## 10. 缺陷与残余问题

严重性按后果定级，不按麻烦程度：

| 等级 | 定义 | 该类的例子 |
| :--- | :--- | :--- |
| **致命** | 静默产出错误结果，或突破了 `requirements.md` 的承诺且没有任何信号 | 布局读取器对压缩形态的文档返回空结果 |
| **严重** | 输出确实错了但可观察，或某个门禁步骤并没有强制它声称的东西 | 一个只断言「文件被写出了」的通过测试 |
| **一般** | 行为正确，但记录、文档或诊断错误或缺失 | 文档里一个过时的数字 |

本次记录带入的未决残余问题：

| # | 问题 | 等级 | 状态 |
| :--- | :--- | :--- | :--- |
| R-1 | `verification.md` 与 `implementations.md` 曾携带过时的测试计数（211 / 79） | 一般 | 已关闭——在同一次改动里对齐到 §9 的数字 |
| R-2 | 没有任何自动化层级施加于真实 draw.io 客户端，因此 `jumpStyle` 跳线与容器标题位置没有自动化证据 | 严重 | 已接受——写在已知限制里 |
| R-3 | SVG 预览不共享 `.drawio` 的边路由器，因此 SVG 边几何不得被断言 | 严重 | 已接受——作为分歧写明，而不是悄悄修 |
| R-4 | 门禁只在一个 runner 上跑；Windows 与 macOS 的行为没有 CI 证据 | 严重 | 已接受——在 §11 记为风险 |
| R-5 | 产物读取器的三个行为（截断输入、版本不匹配、元数据缺失）由合成夹具覆盖，而非真实世界的产物 | 一般 | 已接受 |
| R-6 | 端到端套件缺一个构建好的 `app.o` 就无法运行，因此没有任何自动化层级施加于真实扩展宿主 | 严重 | 已接受——它需要门禁所没有的 C 工具链 |

R-2 至 R-4 也出现在仓库 README 的已知限制里。两份清单不得互相矛盾；一旦矛盾，以更严格的那条为准，
直到其中一份被改正。

## 11. 风险

| 风险 | 影响 | 当前缓解 | 未缓解部分 |
| :--- | :--- | :--- | :--- |
| 金标准在一次无关重构中发生变化 | 手工排版不再匹配，而评审把它当作噪音放过 | 金标准的差异按行为变更评审；没有行为变更却移动的金标准视为 bug | 没有结构性手段——评审靠人工 |
| 某个行为只存在于金标准恰好看到的地方 | 别处的回归一直是绿的 | 显式列出「金标准看不见的行为」，各自配独立测试 | 新增行为若不配测试，就一直不可见，直到有人去写 |
| 平台差异（路径、权限、换行） | Windows 或 macOS 用户遇到门禁看不见的失败 | 跨平台代码路径；输出中不含绝对路径 | 那两个平台上没有任何 CI 覆盖 |
| sidecar 依赖的外部运行时缺失 | 完全读不了 PE/CLI 产物 | 给出可操作的安装提示，而不是静默失败 | 运行时无法随包分发，这是永久性的 |
| 几何被契约冻结 | 任何布局改进都会打破每一个金标准 | 「可以改变算得多快、不能改变算出什么」这条规则 | 是刻意的；放宽它等于让手工排版不再被钉住 |
| 数字与现实脱节 | 读者相信了过时的数字 | 本节记录规则 | 依赖变更纪律被执行；R-1 说明它确实会滑 |

## 12. 变更协议

| 若你改动了… | 你还必须更新… | 因为… |
| :--- | :--- | :--- |
| 任何被需求覆盖的行为 | `requirements.md` 中的对应条目 | 需求是权威，本文档只负责证明 |
| 任何测试、任何门禁步骤、任何命令 | 本文档 §3、§8 与 §9 | 门禁是契约，会漂移的就不叫契约 |
| 任何被测量的数字 | 本文档 §9 **以及** `verification.md` | 两处都持有数字，它们必须一起动 |
| 比对规则或容差 | `conformance.md` | 比对语义定义在那里，不在这里 |
| 哪些被验证、哪些没有 | 本文档 §10、`docs/limitations.md`、README 的已知限制 | 三份清单描述的是同一批残余风险 |
| 产物夹具或金标准用例 | 本文档 §9 以及 `conformance.md` 的比对说明 | 用例清单是记录的一部分 |
| 本仓任何文档 | 它的中文版，且在同一次改动内 | 单一语言的文档就是缺陷 |

## 附录——引用结构的裁剪说明

本文档的章节骨架改编自一套 GJB 质量记录包（STP / STD / STR、型式试验、计量校准、电气安全、
9001C 设计记录集）。以下章节被整体删除，因为它们描述的是硬件交付物，对一个 VS Code 扩展没有
可观测对象：

| 被删除的章节 | 为什么不适用 |
| :--- | :--- |
| 硬件环境（温湿度、供电、机柜） | 交付物是 VSIX，运行环境是用户机器上的 VS Code |
| 型式试验、环境应力筛选、EMC 发射与敏感度 | 没有物理实体，也没有电磁发射 |
| 计量校准、溯源链、测量不确定度 | 没有测量仪器；「准确」由断言而非仪器保证 |
| 电气安全、接地、绝缘耐压 | 同上 |
| 设计评审 / 验证 / 确认 / 更改记录（9001C 8.3） | 单人维护、无独立评审方；该职责由 §8 的门禁与 §12 的变更协议承担 |
| 进度安排与人员资源（STP §5.2 / 5.3） | 没有可记录的排期与角色分工 |

被保留并改写成软件语境的是：范围、测试级别与类型、测试环境、测试项清单（§7 追踪表）、
准入与准出、需求追踪、测试记录、缺陷与失败处理、风险。

写这一节的目的，是让刻意的裁剪不被误认为缺失的章节。
